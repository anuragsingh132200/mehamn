# Engineering note

Mira uses an LLM to interpret conversation, resolve references, propose typed tool calls, and write responses. The versioned formal prompt is in `backend/app/prompts.py`. Native OpenAI function calling submits a strict `AgentDecision` containing an ordered allowlisted tool batch. Server-owned identity and validated arguments control execution. A second planning round can adapt to tool results; response generation uses verified fact references for exact amounts and booking status. No runtime keyword parser remains.

Defaults bound a turn to two planning rounds, four model calls including repairs/response generation, twelve dispatched calls, twelve recent messages, and a 55-second model deadline. Model token usage and call counts are recorded. Missing credentials fail explicitly. If response generation fails after a successful mutation, a backend receipt preserves the hold and request idempotency.

The conversation row is authoritative. A PostgreSQL `FOR UPDATE` lock serializes chat messages and manager decisions for the session across stateless workers. State versions support optimistic client conflicts. History is paginated separately. Requirement changes invalidate quotes, offers, recommendations, and pending confirmation. Existing inventory holds remain valid until expiry and are displayed separately. PostgreSQL LangGraph checkpoints provide node snapshots; they are diagnostic rather than a second booking authority. Checkpoint writes use a separate connection, so a snapshot may precede a rolled-back booking transaction. New messages always start from committed conversation state; automatic checkpoint replay of mutation nodes is intentionally unsupported.

Inventory is calculated for every night with exclusive checkout, subtracting confirmed fictional reservations, restrictions, and unexpired holds. A hold transaction locks the room-type inventory row before checking availability, validating quote ownership, fingerprint, expiry, and pricing-policy version, and inserting the hold. Locking the entire room type is deliberately conservative: it prevents overlapping stay races with a small, understandable contention domain, at the cost of serializing non-overlapping holds for that room. A database unique constraint plus per-session lock handles repeated idempotency keys. Concurrent PostgreSQL tests prove only one session can obtain the last villa and that concurrent session messages increment versions without losing turns.

Monetary values are integer paise. Tax uses Decimal half-up rounding; discount threshold decisions use exact integer cross multiplication. Approved amounts never round below the permitted floor. Per-property policies determine auto approval, manager review, or counteroffer. Every offer records quote, status, amount, policy version, and expiration. Changes expire stale offers. Manager decisions require a separate secret header and create an audit trace; the assistant cannot fabricate approval. Flagging uses observable categories. Repeated negotiation is an informational review event, never proof of fraud. Unknown amenities remain unknown, and obvious instruction overrides are ignored and flagged.

Each worker has pooled SQL and checkpoint connections, server-side query/lock timeouts, request IDs, redacted JSON logs, bounded pagination, and database-backed per-session chat rate limits. No Redis, queues, payment service, or vector database is needed. Public endpoints and session creation still need ingress rate limiting before internet deployment. Demo bearer tokens and the manager secret are intentionally simpler than production identity; add TLS, secret rotation, retention, authorization audit, and operational monitoring for a real rollout.

Current verification uses mocked structured model outputs, actual PostgreSQL concurrency tests, and a production frontend build. See REFACTOR_REPORT.md for measured results and live-model limitations. Prior HTTP/browser/load artifacts describe the pre-refactor baseline only.
